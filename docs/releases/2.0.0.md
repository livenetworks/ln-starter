# LN-Starter 2.0.0 — 2026-08-20

2.0.0 replaces the passwordless authentication flow, adds a structured security
event pipeline, and defines a production support contract. **Every installation
upgrading from 1.x needs configuration changes before it will boot.**

## Why this is a major version

Per the public API defined in [ADR 0004](../adr/0004-versioning-release-and-distribution.md),
the following are breaking. Any one of the first three forces a major on its own.

| # | Change | What breaks |
|---|---|---|
| 1 | Route names `auth.magic.show` and `auth.magic.consume` removed | `route('auth.magic.show')` throws `RouteNotFoundException` |
| 2 | `auth.peppers.current` and `auth.peppers.keys` are now required | **The service provider throws during boot.** An upgrade that changes no config does not degrade — it fails to start |
| 3 | `AuthController::magicShow()`, `magicConsume()`, `magicStatus()`, `magicWait()` removed | Subclasses and direct references break |
| 4 | `POST /logout` moved from `auth:sanctum` + `disable-csrf` to `auth:web` with CSRF | A bearer client posting without a CSRF token now receives 419 |
| 5 | Published views `magic_wait.blade.php` and `magic_success.blade.php` removed | `ln-starter:install` **refuses to run** while either is still published. Both are detected by name; any other published `auth/` or `emails/` view is flagged by content when it references a removed route or a legacy field |
| 6 | `create_magic_link_tokens_table.php` no longer loaded or published | The file remains in the tree but is in no publish tag |
| 7 | The Sanctum personal-access-token migration moved to its own tag | `vendor:publish --tag=ln-starter-migrations` no longer yields it; use `--tag=ln-starter-sanctum-migrations` |
| 8 | `/magic/wait` and `/magic/status` changed semantics | Compatibility shims for one release; see below |
| 9 | Security event names renamed to the catalogue | Log pipelines matching the previous ad-hoc names stop matching |

**Not a breaking change, stated because it is easy to assume otherwise:** the
dependency constraints are unchanged from 1.2.1. `php ^8.3` and
`illuminate/* ^11.0|^12.0|^13.0` are identical in both. Nothing here is caused
by dropping an old framework.

### Added

- `logging` config tree, `SecurityEventLogger`, the `SecurityAuditSink` contract
- Middleware aliases `ln.locale.prepare`, `ln.locale.redirect`, and `ln.request-id`
- Publish tags `ln-starter-security-migrations`, `ln-starter-sanctum-migrations`
- Commands `ln-starter:auth-v2-audit`, `ln-starter:auth-v2-readiness`,
  `ln-starter:auth-v2-cutover`, `ln-starter:security-audit-prune`
- Components `<x-ln.logout-form />`, `<x-ln.lang-switcher />`

### Deprecated, not removed

- The `cookie.auth` / `auth_token` bridge. Auth v2 neither issues nor reads it.
  It remains available for consumer-owned bearer APIs and is removed in 3.0.0.

## Security

- Replaces the polling + personal-access-token magic login with a single-use,
  row-locked link-plus-code state machine that authenticates a normal Laravel
  `web` session. The link `GET` never consumes a proof and never
  authenticates; a CSRF-protected `POST` consumes exactly one proof under a
  database lock.
- Keeps CSRF protection for session and cookie-authenticated requests even when
  a bearer header is also present. Only `disable-csrf:bearer` routes carrying an
  explicit `Authorization` bearer token are excluded, and a cookie-derived
  bearer header is never exempt.
- Stores only purpose-separated proof digests, binds codes to the requesting
  session, and supports versioned HMAC pepper rotation.
- Invalidates the session and rotates the CSRF token on logout.
- Delegates `sanctum.token` to Sanctum's official guard, preserving expiry,
  provider checks, events and usage tracking.
- Emits allow-listed security events carrying no email, token, code, cookie,
  authorization header, request body or session secret.
- Fails production readiness when the database cannot provide transactional row
  locking — SQLite, or a non-InnoDB `magic_login_attempts` table — because
  `lockForUpdate()` is silently a no-op there and single-use consumption would
  not be atomic.
- Renders the auth pages without a frontend build. Previously the shipped layout
  called Vite unconditionally, so an installation that had not run `npm run
  build` returned HTTP 500 on `/login`: a skipped asset build took
  authentication down.

## Auth v2 state machine

A magic-login attempt is a row in `magic_login_attempts` moving through
`pending → consumed`, or to a terminal `expired` / `revoked`.

1. `POST /auth/magic-link` validates the email and dispatches an **encrypted**
   queue job. The response is identical whether or not the account exists.
2. The job checks eligibility and mails a high-entropy link plus a six-digit
   code bound to the requesting session.
3. `GET /auth/magic/{token}` **neither consumes the proof nor authenticates**,
   and issues no credential. It is not inert: it establishes a session-bound
   confirmation context, applies the open throttle and emits an audit event,
   then redirects to a token-free confirmation URL.
4. `POST /auth/magic/confirm/{context}` consumes the proof: inside a
   transaction, `lockForUpdate()` on the attempt row, verify, mark consumed,
   commit, then start the session.
5. Events are **staged and emitted after commit**, so a rollback cannot produce
   a false success. Under concurrency exactly one winner reports
   `auth.magic.proof.accepted`; the loser reports `auth.magic.proof.replayed`.

No polling. No personal access token. Only digests are stored, and nothing
secret reaches a log. The raw token does appear once, in the emailed link —
unavoidably, since that is what a magic link is — and the first navigation
replaces it with a token-free confirmation URL, so it never reaches the address
bar of a later request, a referrer header or the browser history of the
confirmation step.

## Observability

Every auth event goes through `SecurityEventLogger` — never `Log::` directly.
Each carries a versioned envelope, a constrained `ReasonCode` rather than a raw
exception message, a pseudonymous `principal_key` rather than an email, IP or
session id, and a real monotonic `duration_ms`.

Context is allow-listed: keys not registered in `logging.context_allow_list` are
dropped. Correlation ids come from `ln.request-id` and are inherited by the
queued mail job. Sinks are added by implementing `SecurityAuditSink` and calling
`SecurityEventDispatcher::extend()`. **Sink failures are fail-open** — auditing
never breaks a login.

The database sink is opt-in (`LN_SECURITY_AUDIT_DB=true`) and its migration is
published separately.

## Configuration

### Required

| Variable | Purpose |
|---|---|
| `LN_AUTH_PEPPER` | 32-byte pepper for proof digests. **The provider throws without it.** |
| `LN_AUTH_PEPPER_ID` | Pepper version id. Defaults to `v1` |

Only `LN_AUTH_PEPPER` blocks boot. Generate it as 32 random bytes,
base64-encoded, and rotate it independently of `APP_KEY`.

### Strongly recommended in production

| Variable | Purpose |
|---|---|
| `LN_SECURITY_PSEUDONYM_KEY` | Key for pseudonymous principal identifiers. **Not** a boot requirement: it falls back to an `APP_KEY`-derived value. Set it explicitly so rotating `APP_KEY` does not silently re-pseudonymise every identifier in your audit history |

### Optional

`LN_SECURITY_PSEUDONYM_ID`, `LN_SECURITY_LOG_ENABLED`, `LN_SECURITY_LOG_CHANNEL`,
`LN_SECURITY_LOG_FALLBACK_CHANNEL`, `LN_SECURITY_LOG_MAX_DEPTH`,
`LN_SECURITY_LOG_MAX_FIELDS`, `LN_SECURITY_LOG_MAX_VALUE`,
`LN_SECURITY_AUDIT_DB`, `LN_SECURITY_AUDIT_CONNECTION`,
`LN_SECURITY_AUDIT_RETENTION_DAYS`, `LN_REQUEST_ID_HEADER`.

### Production requirements

`ln-starter:auth-v2-readiness` fails closed on each of these:

| Area | Requirement |
|---|---|
| Database | MySQL/**InnoDB** or PostgreSQL. SQLite is refused: `lockForUpdate()` is a no-op |
| Session | `session.secure`, `session.http_only`, a same-site policy, and **no parent-domain** `session.domain` |
| Transport | `APP_URL` must be `https` with a non-empty host |
| Queue | A real queue connection. `sync` defeats the enumeration-resistant response timing |
| Mail | A configured mailer |
| Peppers | Current pepper id present in the key set |

## Published views

Consumer overrides under `resources/views/vendor/ln-starter/` are **never**
overwritten. `ln-starter:install` audits them and refuses to run while a v1 view
that auth v2 removed is still published, naming the exact paths. This is
deliberate: a leftover `magic_wait.blade.php` polls endpoints that no longer
issue credentials, and a leftover `magic_success.blade.php` is dead weight that
nothing renders.

The two removed views are matched **by name**, because a published copy need
not contain anything recognisable — the shipped `magic_success.blade.php`
references no removed route and no legacy field, so a content scan would never
find it. Every other published `auth/` or `emails/` view is matched by content.

**Delete** the two removed views; there is nothing to port, since auth v2 has
neither a wait page nor a success page. Port your customisations of the views
that still exist. `ln-starter:auth-v2-audit` reports the same set at any time
and exits non-zero while any remain.

## Legacy endpoints

For **one release only**, per [ADR 0001](../adr/0001-magic-link-authentication-v2.md) §4:

| Endpoint | Behaviour |
|---|---|
| `GET /magic/wait` | Redirects to the v2 login page with the generic message |
| `GET\|POST /magic/status` | HTTP 410 with `{"ok":false,"error":"No session","upgrade_required":true}` |

The 410 payload is what makes an old polling script stop rather than retry a 404
loop. The `POST` variant keeps normal CSRF protection. Neither issues a
credential. **Both are removed in 3.0.0.**

## Fresh install

```bash
composer require livenetworks/ln-starter:^2.0
php artisan ln-starter:install
php artisan migrate
php artisan ln-starter:auth-v2-readiness
```

Set `LN_AUTH_PEPPER` in `.env` **before `composer require`**, not merely before
the first artisan call: package discovery boots the provider during the require
itself and it validates auth configuration, so a missing pepper fails there.

`LN_SECURITY_PSEUDONYM_KEY` is not a boot requirement — it falls back to an
`APP_KEY`-derived value — but set it explicitly in production before you rely
on the audit trail.

The installer publishes config, views and migrations, and injects the auth SCSS
entry into `vite.config.js`. Run `npm run build` for styling; the login page
renders unstyled but fully working without it.

## Upgrade from 1.2.1

Read [`UPGRADE.md`](../../UPGRADE.md) for the full procedure. In order:

1. **Back up the database.** The cutover below destroys data and cannot be
   undone.
2. **Add the required environment variables** (above) *before* anything else.
   Package discovery boots the provider during `composer require`, and it
   validates auth configuration — a missing pepper fails the require itself.
3. **`composer require livenetworks/ln-starter:^2.0`.** This has to come
   before the audit: `ln-starter:auth-v2-audit` does not exist in 1.2.1.
4. **Audit published views** — `php artisan ln-starter:auth-v2-audit`. It
   names every stale path and exits non-zero until none remain. Port or
   delete each one, then re-run until it exits 0.
5. **`php artisan ln-starter:install`.** Required, not optional: it publishes
   the new config, views and migrations, and it refuses to run while a stale
   v1 view is still published — the same refusal the audit reports.
6. **Merge config.** `config/ln-starter.php` merges recursively, so an older
   published file keeps its values and gains the new `auth.peppers` and
   `logging` keys. Review the result; do not blindly republish over your own.
7. **`php artisan migrate`** — adds `magic_login_attempts` and, if you opted
   in, `ln_security_audit_events`. The additive first/last-name migration does
   not replace your users migration.
8. **`php artisan ln-starter:auth-v2-readiness`** and resolve every failure.
9. **Cutover** — `php artisan ln-starter:auth-v2-cutover --force` invalidates
   pending v1 proofs. Users mid-login must request a new link. **Irreversible.**
10. **Rebuild caches** — `config:cache`, `route:cache`, `view:cache`.
11. **Restart queue workers.** Workers hold the old code in memory; the magic
    link is sent from a queued job, so stale workers break login silently.
12. **Smoke test a real login** end to end before announcing the deploy.
13. **Remove the legacy `magic_link_tokens` table** only after the
    compatibility window, once no v1 client remains.

This is the order the upgrade harness executes and CI proves on Laravel 12 and
13; it is not a reconstruction from memory.

## Rollback

`docs/deployment.md` holds the operational procedure. The constraints:

- Downgrading the package does **not** restore proofs destroyed by step 8. If
  you have run the cutover, rolling back leaves those users unable to log in
  with their old link; they simply request a new one.
- The `magic_login_attempts` and `ln_security_audit_events` tables are additive.
  Leave them; a downgraded 1.x installation ignores them.
- The additive `users` columns are additive. Do not drop them to roll back.
- Restore the previous `config/ln-starter.php` and rebuild the config cache.
- Restart queue workers again on the way back.

Prefer a fix-forward patch release over a downgrade, per ADR 0004.

## Consumer checklist

- [ ] Database backup taken and restore tested
- [ ] `ln-starter:auth-v2-audit` exits 0
- [ ] `LN_AUTH_PEPPER` and `LN_SECURITY_PSEUDONYM_KEY` set, and stored in the secret manager
- [ ] `APP_URL` is https; session cookie secure, http-only, same-site, no parent domain
- [ ] Queue connection is not `sync`, and workers restart as part of deploy
- [ ] Mailer configured and a test message delivered
- [ ] `magic_login_attempts` is InnoDB (MySQL) or on PostgreSQL
- [ ] `ln-starter:auth-v2-readiness` exits 0
- [ ] Any `route('auth.magic.show')` / `route('auth.magic.consume')` call replaced
- [ ] Any subclass of `AuthController` checked for the four removed methods
- [ ] Bearer clients posting to `/logout` updated for CSRF, or moved to their own route
- [ ] Log pipeline updated for the renamed security event names
- [ ] Published view overrides ported
- [ ] `npm run build` run if styled auth pages are wanted
- [ ] Smoke login performed against production configuration
